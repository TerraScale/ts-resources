# MCP `2026-07-28`: stateless protocol research and TerraScale guidance

**Research date:** 2026-08-16<br>
**Primary input:** [Cloudflare, “The next generation of MCP”](https://blog.cloudflare.com/mcp-v2/) (2026-08-06)<br>
**Protocol baseline:** [MCP `2026-07-28` specification announcement](https://blog.modelcontextprotocol.io/posts/2026-07-28/)<br>
**Scope:** protocol and deployment implications for `TerraScale.MCP`; this document does not authorize a new transport, public endpoint, or mutation.

## Executive summary

MCP `2026-07-28` makes the protocol layer stateless. The required `initialize`/`initialized` handshake and `Mcp-Session-Id` transport session are gone for the new protocol path. Each request carries the protocol version and client metadata it needs, and an optional `server/discover` call replaces the need for a capability handshake. A remote server can therefore run as an ordinary HTTP workload behind a non-sticky load balancer.

Stateless transport does **not** mean that a product cannot have state. If a workflow needs continuity, the server must make that state explicit: issue a short-lived, authenticated handle and require the client to return it on the next request. Long-running work belongs in the Tasks extension or another durable product workflow, not in hidden MCP transport state.

For TerraScale, the immediate decision is **no production code change**. The repository currently ships a local, read-only stdio server and has no public HTTP MCP endpoint. Keep that boundary. If a remote HTTP deployment is later approved, implement it as a separate transport and security design using the official .NET HTTP transport in explicit stateless mode; do not infer it from the current stdio binary or add a Cloudflare-specific `McpAgent` pattern.

## What changed in `2026-07-28`

### 1. Stateless request path

The new protocol removes protocol-level sessions from the modern path:

- No required `initialize`/`initialized` exchange.
- No `Mcp-Session-Id` header to store, route, expire, or replay.
- Every request carries protocol version, client identity, and client capabilities in request metadata.
- `server/discover` is optional discovery for clients that want capabilities before calling a tool, prompt, or resource.
- Any healthy server instance can process any request; sticky sessions and a shared MCP session store are no longer required.

This is a transport change, not a permission change. Authentication, authorization, tenant/project scope, replay protection, idempotency, and application state still need explicit server-side enforcement.

### 2. Streamable HTTP is one ordinary HTTP endpoint

The modern remote shape is a single `POST /mcp` endpoint. The request includes:

- `MCP-Protocol-Version: 2026-07-28`
- `Mcp-Method`, mirroring the JSON-RPC method
- `Mcp-Name`, identifying the tool/resource/prompt or other operation when applicable
- JSON-RPC content in the body, including per-request `_meta`

Gateways can route, authorize, rate-limit, and observe using headers without parsing JSON-RPC bodies. The server must reject a request when the standard headers disagree with the body. The old HTTP+SSE transport is deprecated; compatibility may require a temporary legacy route, but new deployments should target Streamable HTTP.

### 3. Multi Round-Trip Requests (MRTR)

Server-to-client interactions that previously depended on a held-open stream—especially elicitation—now use a request/response loop. A tool returns an `input_required` result describing the requested input and a request state. The client collects the user response, then retries the original operation with the responses and request state attached.

This removes the transport session, but it does not make an approval trustworthy by itself. Any sensitive or mutating TerraScale operation must still use an upstream, non-agent-controlled approval authority and a server-enforced, short-lived authorization protocol. MRTR is a wire mechanism, not an authorization boundary.

### 4. Explicit application state

The protocol session is gone, but stateful applications remain valid. The recommended pattern is:

1. A tool creates or obtains a server-minted handle.
2. The handle is bound to the authenticated caller, configured project, operation, expiry, and (where relevant) idempotency key.
3. Later calls supply the handle as a typed argument.
4. The server validates the handle before reading or mutating any state.

Do not put bearer credentials, raw database identifiers outside the configured scope, confirmation tokens, or unbounded serialized state in a client-visible handle. A handle is an application credential and must be treated as sensitive.

### 5. Caching, tracing, and extensions

List/resource results can carry cache hints (`ttlMs` and `cacheScope`) and should be returned in deterministic order. This enables safe client caching and improves prompt-cache stability, but cache scope must match the sensitivity and authorization scope of the data.

The specification documents W3C trace context propagation in `_meta` (`traceparent`, `tracestate`, and `baggage`) so a tool call can be correlated across the host, MCP server, gateway, and downstream TerraScale API.

The release also formalizes an extensions framework. Tasks now provide a poll-oriented path for long-running work; MCP Apps and Enterprise-Managed Authorization are extensions rather than implicit core behavior. Roots, Sampling, Logging, Dynamic Client Registration, and legacy HTTP+SSE are deprecated with a minimum twelve-month migration window. New TerraScale work should not adopt deprecated features.

### 6. Authorization hardening

The new authorization guidance prefers pre-registered clients where the relationship is known, then Client ID Metadata Documents (CIMD) for dynamic client identity; Dynamic Client Registration remains only for compatibility. Authorization responses carry issuer information under RFC 9207, and tokens are bound to the MCP resource/audience (RFC 8707). A remote TerraScale MCP endpoint must validate issuer, audience/resource, and caller/project authorization on every request.

## The new stateless usage pattern

For a remote server, the conceptual flow is:

```text
client -> POST /mcp (self-describing 2026-07-28 request)
server -> one JSON result or a request-scoped SSE result stream
client -> optional next POST, independently routable to any instance
```

A minimal server is created per request by a factory. The factory registers the fixed tools/resources/prompts; it must not rely on an in-memory transport session. Durable state, if any, is read through an explicit handle or a product-owned durable store.

For the official .NET SDK, the documented server shape is:

```csharp
builder.Services.AddMcpServer()
    .WithHttpTransport(options => options.Stateless = true)
    .WithTools<MyTools>();

var app = builder.Build();
app.MapMcp();
app.Run();
```

Set `Stateless = true` explicitly even though it is the current SDK default. Set it to `false` only for a deliberate legacy compatibility path that needs unsolicited notifications, resource subscriptions, per-client isolation, or other session-dependent behavior. The C# SDK documents stateful Streamable HTTP as a back-compat escape hatch, not the forward-compatible default.

## Cloudflare’s implementation and migration advice

Cloudflare’s article describes the same protocol shift in its Workers ecosystem:

- `createMcpHandler` receives a server factory and creates an isolated server for each request.
- `McpAgent` and Durable Objects are no longer required merely to speak MCP; they remain appropriate when the application itself needs durable or coordinated state.
- The `/mcp` route accepts the new protocol and stateless 2025-era Streamable HTTP traffic during migration.
- Servers that truly need legacy sessions should run a stateless route beside the sessionful route, migrate features, allow sessions to drain, and then remove the legacy route.

These are useful deployment patterns, not TerraScale dependencies. The Workers SDK, OAuth provider, and Durable Objects are Cloudflare-specific; TerraScale should use the official C# SDK and TerraScale-owned authentication, authorization, and durable workflows.

## TerraScale impact and decisions

### Current state

The current `TerraScale.MCP` program registers `.WithStdioServerTransport()` and exposes a fixed, read-only tool/resource/prompt surface. It uses the public typed TerraScale .NET SDK, fixes scope to `TERRASCALE_PROJECT_ID`, and deliberately has no public HTTP endpoint. Stdout remains JSON-RPC only; diagnostics go to stderr.

The new protocol therefore does not justify changing the current binary, adding an HTTP listener, adding a session cache, or relaxing any existing mutation/scope rules. Stdio remains the appropriate local delivery for this product boundary.

### Future remote-HTTP requirements

If product approval later includes a remote MCP endpoint, the implementation packet must include all of the following before code lands:

1. Add the official .NET HTTP transport as a separate, explicitly stateless entry point at one versioned `/mcp` route; do not repurpose stdio startup or expose internal RPC.
2. Validate HTTPS, `Origin` (including DNS-rebinding defenses), authorization issuer, token audience/resource, and configured-project scope on every request.
3. Validate `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` against the JSON-RPC body before dispatch.
4. Keep tools/resources/prompts deterministic and bounded. Preserve safe projections, redacted errors, timeout limits, and the deny-by-default mutation policy.
5. Use MRTR only for a reviewed interaction contract. It cannot approve or authorize a backup, restore, or other mutation.
6. Represent continuity with typed, short-lived, server-minted handles bound to caller/project/operation, or use an approved durable product workflow. Never rely on process memory or an MCP session ID.
7. Add tests for modern discovery, header/body mismatch, independent-instance routing, auth issuer/audience failures, cache metadata, cancellation/retry behavior, and legacy compatibility if a migration route is retained.
8. Publish a compatibility matrix for the public HTTP contract and SDK consumers before implementation, then validate each producer/consumer boundary.

## Recommended rollout

| Phase | TerraScale action | Exit evidence |
| --- | --- | --- |
| Now | Keep stdio-only, read-only delivery; record this research. | Existing stdio, scope, projection, cancellation, and stderr-isolation tests remain green. |
| Design | Decide whether a remote HTTP product surface is actually needed. Define auth, route ownership, project scope, state handles, and legacy-client policy. | Approved design and compatibility matrix; no mutation admission gap. |
| Implement | Build a separate stateless HTTP host with the official C# SDK; keep the current stdio server intact. | Modern `2026-07-28` protocol tests plus auth/scope/security evidence. |
| Migrate | If legacy HTTP clients must be supported, run explicit dual paths, observe and drain old sessions, then remove the legacy path within the deprecation window. | Client inventory, drain evidence, and a removal decision. |
