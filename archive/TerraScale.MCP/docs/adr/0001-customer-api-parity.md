# Target customer API parity in MCP

TerraScale MCP may expose every supported customer-facing public API capability, including mutations, but it never exposes private operator or control-plane APIs or a generic raw-request escape hatch. Each tool must pass tenant-isolation and live authorization tests before release. Destructive, costly, credential, membership, billing, restore, and region-placement operations use a two-step flow. The first tool returns the exact plan, impact, price where relevant, and a short-lived confirmation token. A separate confirmed tool consumes that token once with idempotency and writes an audit record.

MCP authenticates with a distinct user-bound MCP access key, never a Project Application credential. The User selects Organization, Project, and operation scopes, and later-created Organizations and Projects are excluded by default. Sensitive-operation confirmation happens in the AI conversation: the AI invokes the confirmed tool with the server-issued five-minute single-use token. The public server rechecks live authority, tenant scope, canonical payload, target state, and price before atomically consuming the token and recording the Audit event. This flow requires neither Dashboard confirmation nor a separate fresh-authentication challenge.

[customer-api-parity.v1.json](../customer-api-parity.v1.json) classifies the complete customer capability families. Its fixed-project read-only classification is historical and must be replaced as typed public operations pass [mutation admission](../design/mcp-mutation-admission.md), including live success, denial, confirmation, tenant-isolation, Audit, idempotency, and secret-handling evidence. Missing evidence blocks the affected operation, not unrelated typed operations that already satisfy the contract.
