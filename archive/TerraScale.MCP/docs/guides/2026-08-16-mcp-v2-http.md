# MCP `2026-07-28` HTTP host

This guide documents the additive HTTP host implemented in
[`src/TerraScale.MCP.Http`](../../src/TerraScale.MCP.Http) and its transport-neutral
composition boundary in
[`src/TerraScale.MCP.Core`](../../src/TerraScale.MCP.Core). It is intentionally
separate from the local stdio host in [`src/TerraScale.MCP`](../../src/TerraScale.MCP).

The repository decision is to add a separate, stateless HTTP executable with
fail-closed, configurable authentication. It does not convert the stdio executable
into a listener, introduce an MCP session store, or broaden the read-only tool
surface. The repository implementation can be built and tested independently, but
production route values, issuer registration, caller-client inventory, TLS, and
ingress remain deployment inputs and operational gates owned by
`TerraScale.Orchestrator`.

## What is implemented

`TerraScale.MCP.Http` is an ASP.NET Core executable that:

- references `TerraScale.MCP.Core` rather than making the stdio host reference
  ASP.NET Core;
- registers the existing safe tools, resources, and prompts through the shared
  `TerraScaleMcpComposition` boundary;
- uses `ModelContextProtocol.AspNetCore` 2.0.0 and explicitly sets
  `WithHttpTransport(options => options.Stateless = true)`;
- maps one canonical MCP route at `/mcp` (modern calls use `POST`);
- constructs caller-bound SDK access through a scoped context and an exchanged token,
  with no MCP session cache or caller/project state in process memory;
- bounds MCP request bodies to 64 KiB and SDK JSON responses to 64 KiB;
- keeps diagnostics on stderr through the console logger and filters the MCP and
  OAuth HTTP-client categories; and
- exposes only safe, read-only projections, including the existing backup-plan
  handoff. It has no backup execution route and never returns a Platform
  confirmation token.

The public MCP resource is configured as the canonical `<authority>/mcp` URI. The
host also maps the standard protected-resource metadata path
`GET /.well-known/oauth-protected-resource/mcp` and non-sensitive liveness and
readiness paths `GET /health/live` and `GET /health/ready`. These paths return no
project metadata, credentials, claims, or diagnostics. The middleware still enforces
the HTTPS/loopback transport rule for them.

## Build a separate HTTP artifact

The stdio bundle remains the release path for the five platform `.mcpb` and
standalone archives; the HTTP executable is never placed inside those stdio
payloads. The release pipeline may emit separate HTTP archives/evidence alongside
them. For source validation, publish the HTTP host as its own output:

```sh
dotnet publish src/TerraScale.MCP.Http \
  -c Release -r linux-x64 --self-contained false \
  -o artifacts/http/linux-x64
```

Use the repository's pinned SDK from `global.json`. The HTTP release artifact,
RID archives, checksums, SBOM, and provenance are separate from the stdio bundle
evidence. To create and verify the complete five-RID HTTP candidate, use:

```sh
dotnet run --project tools/TerraScale.MCP.Bundle -c Release -- --http
dotnet run --project tools/TerraScale.MCP.Bundle -c Release -- --http --verify
```

The HTTP archives and evidence are written under `artifacts/mcp-http/` as
`terrascale-mcp-http-<rid>.zip`, `checksums.json`, `candidate-sbom.cdx.json`, and
`candidate-evidence.json`. The direct `dotnet publish` command above is only a
source-build example. Candidate packaging requires the same clean-worktree and
locked-restore admission as the stdio packager. This repository does not publish an
external Forgejo release or configure a production route.

## Deployment configuration

The process reads these exact environment variables at startup. Required values are
bounded and reject control characters. URI values must be absolute HTTP(S) URIs
without user information or fragments. Do not put secrets in source, logs, tool
arguments, prompts, or this documentation.

| Variable | Required | Validation and use |
| --- | --- | --- |
| `TERRASCALE_API_BASE_ADDRESS` | Yes | Public TerraScale API base URI used by the typed SDK after exchange. |
| `TERRASCALE_PROJECT_ID` | Yes | Fixed project boundary for every scoped SDK read; token `project_id` must contain this exact value. |
| `TERRASCALE_MCP_ISSUER` | Yes | Exact trusted issuer URI. The RFC 7662 response `iss` must equal it byte-for-byte. |
| `TERRASCALE_MCP_RESOURCE` | Yes | Exact MCP resource URI. Its path must be `/mcp` and it must have no query; the protected-resource metadata advertises this value. |
| `TERRASCALE_MCP_INTROSPECTION_ENDPOINT` | Yes | RFC 7662 introspection endpoint called with the server's confidential client. |
| `TERRASCALE_MCP_TOKEN_ENDPOINT` | Yes | RFC 8693 token endpoint called with the server's confidential client. |
| `TERRASCALE_MCP_CONFIDENTIAL_CLIENT_ID` | Yes | Pre-registered MCP host client ID for OAuth Basic authentication. It may not contain `:`. |
| `TERRASCALE_MCP_CONFIDENTIAL_CLIENT_SECRET` | Yes | Secret for that pre-registered host client. Keep it in deployment secret management. |
| `TERRASCALE_MCP_REQUIRED_SCOPE` | Yes | One exact, whitespace-free caller scope required by introspection. |
| `TERRASCALE_MCP_ALLOWED_CLIENT_IDS` | Yes | One or more comma-separated, pre-registered caller `client_id` values. |
| `TERRASCALE_API_RESOURCE` | Yes | TerraScale API resource URI sent in the RFC 8693 exchange request. |
| `TERRASCALE_API_SCOPE` | Yes | One exact, whitespace-free TerraScale API scope sent in the exchange request. |
| `TERRASCALE_MCP_ALLOWED_ORIGINS` | No | Comma-separated origin roots. Each value must be a scheme/host/port with `/` as its only path and no user info, query, or fragment. |
| `TERRASCALE_MCP_ALLOW_INSECURE_LOOPBACK_HTTP` | No | Only the literal `true` opts into development HTTP. The opt-in is still restricted to a loopback peer and all-loopback configured endpoints. |

The HTTP host rejects either stdio credential variable when present:
`TERRASCALE_BEARER_TOKEN` and `TERRASCALE_API_KEY`. Those variables belong to the
local stdio process and cannot be used as a shared operator credential for remote
callers. The HTTP host has no fallback credential mode.

### Production and local URI rules

All configured endpoint URIs must use HTTPS by default. The explicit development
exception is narrow:

1. `TERRASCALE_MCP_ALLOW_INSECURE_LOOPBACK_HTTP` must equal `true`.
2. The incoming request peer must be loopback (`127.0.0.1`, `::1`, or equivalent).
3. Every configured URI (`TERRASCALE_API_BASE_ADDRESS`, issuer, MCP resource,
   introspection endpoint, token endpoint, and API resource) must itself be
   loopback.

An HTTP URI for any non-loopback host is rejected at startup even when the flag is
set. A non-HTTPS request from a non-loopback peer receives `https_required`. In
production, the deployment must arrange for `HttpRequest.IsHttps` to be true at the
host boundary and provide the TLS/forwarding behavior through the approved hosting
path; no ingress or Kubernetes configuration is added here.

### Origin policy

If a request includes `Origin`, it must contain exactly one value. The host parses
and normalizes it to `scheme://idn-host:port` and compares it to the exact configured
set in `TERRASCALE_MCP_ALLOWED_ORIGINS`. A present but malformed, multiple, or
unconfigured origin is rejected with the safe `origin_forbidden` response. A request
without `Origin` is allowed by this middleware, which supports non-browser clients;
browser deployments should always configure their exact allowed origins and enforce
the same policy at the ingress layer.

## Caller authentication and API authorization

The HTTP host uses a two-token-boundary flow. A remote caller supplies a bearer token
to `POST /mcp`; the host never passes that token through to TerraScale.

### 1. RFC 7662 introspection

For each MCP request, the host sends a form-encoded request to
`TERRASCALE_MCP_INTROSPECTION_ENDPOINT`:

```text
token=<caller access token>
```

It authenticates that request with HTTP Basic using the pre-registered
`TERRASCALE_MCP_CONFIDENTIAL_CLIENT_ID` and
`TERRASCALE_MCP_CONFIDENTIAL_CLIENT_SECRET`. The response must be an object with
`active: true`, a bounded `sub`, and a future integer `exp`. The following checks
are strict:

| Introspection value | Required condition |
| --- | --- |
| `iss` | Exact match for `TERRASCALE_MCP_ISSUER`. |
| `aud` | String or array containing the exact `TERRASCALE_MCP_RESOURCE`. |
| `client_id` | Exact member of `TERRASCALE_MCP_ALLOWED_CLIENT_IDS`. |
| `scope` | Space-delimited values contain the exact `TERRASCALE_MCP_REQUIRED_SCOPE`. |
| `project_id` | String or array containing the exact `TERRASCALE_PROJECT_ID`. |
| `sub` and `exp` | Present, bounded, and not expired. |

Missing/malformed/inactive credentials receive `401 unauthorized` and a
`WWW-Authenticate` value pointing to the configured protected-resource metadata.
An active token that fails issuer, resource, client, scope, project, or expiry
authorization receives `403 forbidden`. Error bodies never contain token claims,
headers, provider responses, exception text, or request IDs. A bounded `session_id`
claim is retained only to enforce the existing read-only backup-plan handoff gate;
it is not a transport session, approval, or routing key.

Caller client IDs are deployment allowlist values. They must be pre-registered with
the authorization authority before rollout. This implementation does not add Client
ID Metadata Documents or Dynamic Client Registration, and it does not infer a caller
identity from `_meta`, tool arguments, or a client-generated handle.

### 2. RFC 8693 token exchange

The typed TerraScale SDK client is created with a caller-bound token provider. When
the SDK needs an API credential, the host sends a form-encoded RFC 8693 request to
`TERRASCALE_MCP_TOKEN_ENDPOINT`, again using the pre-registered host client:

```text
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
subject_token=<caller access token>
subject_token_type=urn:ietf:params:oauth:token-type:access_token
requested_token_type=urn:ietf:params:oauth:token-type:access_token
resource=<TERRASCALE_API_RESOURCE>
scope=<TERRASCALE_API_SCOPE>
```

The exchange response must contain a non-empty, bounded `access_token`, exact
`issued_token_type: urn:ietf:params:oauth:token-type:access_token`, and a
case-insensitive `token_type: Bearer`; an optional `expires_in` must be a positive
integer. Only this exchanged token is supplied to the public typed SDK. Exchange
failures are reduced to `request_failed`; no token is logged or returned to the MCP
client. There is no shared TerraScale operator bearer token and no passthrough of
the inbound MCP credential.

All existing SDK calls remain rooted in `TERRASCALE_PROJECT_ID`, and the shared
safe services verify parent and child project/database scope before projection.
The HTTP host does not add generic requests, private routes, internal RPC, direct
storage, or mutation tools.

## Protected metadata and health endpoints

For a configured resource such as `https://mcp.example.test/mcp`, the host exposes:

```http
GET /.well-known/oauth-protected-resource/mcp
```

The response is the bounded protected-resource metadata shape:

```json
{
  "resource": "https://mcp.example.test/mcp",
  "authorization_servers": ["https://issuer.example.test"],
  "bearer_methods_supported": ["header"],
  "scopes_supported": ["mcp:invoke"]
}
```

The concrete resource, issuer, and scope above are examples only; production values
are deployment inputs. The liveness and readiness responses are intentionally
minimal:

```http
GET /health/live
GET /health/ready
```

```json
{"status":"ok"}
```

The host also advertises the metadata URI in `WWW-Authenticate` for a missing or
invalid bearer credential. Health and metadata are not a substitute for an ingress
readiness gate or live issuer/client verification.

## MCP `2026-07-28` request examples

The modern path is one independently routable `POST /mcp` per request. There is no
`initialize`/`initialized` handshake and no `Mcp-Session-Id` requirement or session
cache. The official transport expects the version and client capabilities in the
body `_meta`; the version header must match the `_meta` value. `Mcp-Method` mirrors
the JSON-RPC method, and `Mcp-Name` mirrors `params.name` or `params.uri` for tool,
resource, and prompt operations.

### Discovery without initialize

`server/discover` is a normal modern request. It does not have an operation name, so
`Mcp-Name` is not sent:

```http
POST /mcp HTTP/1.1
Host: mcp.example.test
Authorization: Bearer <caller-access-token>
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: server/discover

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "example-client",
        "version": "1.0.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

`protocolVersion` and `clientCapabilities` are the required per-request metadata;
the `clientInfo` object is included here as the recommended caller identity
metadata. These self-reported fields are informational and are not authorization.

### Tool call with headers and `_meta`

For a tool call, `Mcp-Name` must match the body `params.name`:

```http
POST /mcp HTTP/1.1
Host: mcp.example.test
Authorization: Bearer <caller-access-token>
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: get_configured_project

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_configured_project",
    "arguments": {},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "example-client",
        "version": "1.0.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

If a client sends a header/body mismatch, an unsupported or missing modern version,
or a malformed request, it must fail at the protocol boundary without dispatching a
tool. Do not send credentials in `_meta` or tool arguments.

### Request-scoped SSE result

When the client advertises `text/event-stream`, the same request may return one
request-scoped SSE result instead of a single JSON response:

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

event: message
data: {"jsonrpc":"2.0","id":2,"result":{"content":[{"type":"text","text":"{\"projectId\":\"project-redacted\"}"}]}}

```

The response stream belongs only to that request and closes after the result. A
subsequent request may be handled by any healthy instance. The modern path does not
mint, require, store, or echo `Mcp-Session-Id`; do not add sticky routing or a
session store around it. The server may instead return one JSON result when the
client's `Accept` negotiation selects JSON.

## Stdio compatibility and safety boundary

The existing stdio host remains the local delivery:

- `src/TerraScale.MCP/Program.cs` still configures
  `.WithStdioServerTransport()`;
- stdout remains exclusively the MCP JSON-RPC stream and diagnostics remain on
  stderr;
- stdio keeps its own `TERRASCALE_BEARER_TOKEN` / `TERRASCALE_API_KEY` configuration;
- the existing five-platform `.mcpb` and standalone archives remain unchanged in
  shape and purpose; and
- the HTTP host does not become selectable through an untrusted mode flag in that
  executable.

The HTTP artifact is therefore released and rolled back independently. A change to
HTTP hosting must not weaken stdio protocol resilience, safe projections, response
limits, cancellation, or mutation-deny behavior.

## Deployment gate, rollout, and rollback

The MCP repository owns the HTTP executable and its deterministic source/configuration
checks. `TerraScale.Orchestrator` owns production hosting, ingress, TLS, route
admission, health probes, client registration, issuer/resource inventory, and
rollout. No production endpoint is implied by a successful local build.

Before enabling a route, the deployment owner must supply and record (outside this
repository where appropriate):

- the exact HTTPS route and `TERRASCALE_MCP_RESOURCE` value;
- the issuer and RFC 7662/RFC 8693 endpoint values;
- the pre-registered confidential host client and allowlisted caller client IDs;
- the API resource/scope and fixed project value;
- TLS/forwarding behavior that preserves the host's HTTPS check;
- exact allowed browser origins, if browser clients are in scope;
- a private or allow-listed first cohort, horizontal routing/readiness evidence,
  denial telemetry, and a live issuer/client fixture; and
- an operational owner and expiry for any shared deployment/test fixture lease.

The current repository has no production issuer, caller-client inventory, concrete
route, live authentication result, or ingress deployment evidence. Those are gaps,
not defaults. The HTTP implementation must not be declared production-ready until
the Orchestrator gate and live authorization evidence are recorded.

To roll back an HTTP release:

1. Disable the `/mcp` route at the owning host/ingress.
2. Revoke or disable the remote caller-client registrations and resource/audience
   authorization at the authority, as required by the incident.
3. Preserve the last approved stdio `.mcpb`/standalone artifact and its local
   configuration as the supported delivery.
4. Investigate and redeploy a separately validated HTTP artifact only after the
   route, issuer, client, and scope evidence is refreshed.

Rollback must not reintroduce a hidden MCP session cache, shared operator token,
token passthrough, mutation behavior, or an unreviewed ingress route.
